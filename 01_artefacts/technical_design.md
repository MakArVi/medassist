# Техническая проработка: ассистент с контекстом пациента из базы клиники

Дата: 2026-10-04. Основа: идея команды «ассистент берёт из базы клиники информацию о клиенте, который сейчас придёт», `mvp_description.md`, `team_synthesis.md`.
Пункты ⚠️ — допущения, их нужно проверить на интервью и у IT пилотной клиники. Конкретные МИС и их API в `00_input/` не описаны, поэтому здесь они не выдуманы.

## 1. Что меняется в продукте

Раньше: ассистент слушает приём и пишет протокол «с нуля».
Теперь: **до приёма** ассистент уже знает пациента, а **после приёма** сверяет разговор с его историей.

Что это даёт:
1. **Перед приёмом:** врач за 10–20 секунд видит краткую сводку (кто пришёл, с чем записался, что было раньше, аллергии, хронические диагнозы, принимаемые препараты).
2. **Во время приёма:** ассистент не переспрашивает известное и понимает контекст («как давление после тех таблеток?»).
3. **После приёма:** черновик протокола содержит только новое, а неизменное подтягивается из истории; расхождения подсвечиваются («в карте аллергия на пенициллин, в разговоре не упомянута»).

⚠️ Это сильнее отстраивает нас от «голос → текст» конкурентов, но требует интеграции с МИС, которую раньше отложили на после MVP (см. раздел 8).

## 2. Как это работает: сквозной сценарий

| Шаг | Что происходит | Где |
|---|---|---|
| 1 | Пациент записан на приём в МИС (или регистратура отметила «пришёл») | МИС клиники |
| 2 | Коннектор получает событие или опрашивает расписание врача на ближайшие приёмы | Контур клиники |
| 3 | Для приёма запрашиваются данные пациента по идентификатору записи | МИС → коннектор |
| 4 | Данные приводятся к единому формату, лишнее отбрасывается, ПДн обезличиваются | Сервис контекста |
| 5 | LLM строит краткую сводку; сводка появляется у врача в приложении | Приложение врача |
| 6 | Врач нажимает «начать приём»; запись и расшифровка идут как в MVP | Приложение, ASR |
| 7 | LLM получает контекст + расшифровку и формирует черновик по шаблону специальности | Оркестратор LLM |
| 8 | Врач правит и подтверждает; текст возвращается в МИС (на старте — копированием) | Приложение, МИС |
| 9 | Контекст пациента удаляется из кэша; в журнале остаётся запись о доступе | Сервис контекста |

## 3. Архитектура

```
[МИС клиники] ──► [Коннектор в контуре клиники] ──► [Сервис контекста пациента] ──┐
   (расписание,        (чтение, фильтр полей,         (нормализация, кэш с TTL,    │
    карта, анализы)     обезличивание)                  журнал доступа)             ▼
                                                                          [Оркестратор LLM] ◄── [ASR + диаризация]
                                                                                 │                    ▲
                                                                                 ▼                    │
                                                                      [Приложение врача: сводка → запись → редактор]
                                                                                 │
                                                                                 ▼
                                                                  [Возврат в МИС] + [Кабинет клиники: статистика]
```

| Блок | Задача | Решение ⚠️ |
|---|---|---|
| Коннектор | Единственная точка, которая «ходит» в МИС; читает только разрешённые поля | Небольшой агент в контуре клиники или облачный адаптер к API МИС |
| Сервис контекста | Приводит данные разных МИС к единой модели пациента, хранит на время приёма | Единая внутренняя схема; кэш с автоудалением |
| Оркестратор LLM | Собирает промпт: шаблон специальности + контекст + расшифровка | YandexGPT / GigaChat / open-source в РФ |
| ASR | Речь → текст с разделением ролей | SpeechKit / GigaAM / Whisper |
| Приложение врача | Сводка → запись → редактор → экспорт | PWA, как в MVP |
| Журнал аудита | Кто, когда и какие данные пациента видел | Отдельное неизменяемое хранилище |

## 4. Способы получить данные из базы клиники

Это главный технический вопрос: **как** мы читаем данные. Варианты от простого к сложному:

| Вариант | Как работает | Плюсы | Минусы | Когда |
|---|---|---|---|---|
| **A. Ручной ввод / загрузка** | Врач или регистратор вставляет выписку или загружает файл; для демо — тестовые карточки | Работает без МИС, дёшево, безопасно | Врач тратит время, нет автоматики | Прототип, интервью, демо |
| **B. API МИС** | Запросы к официальному API (REST, HL7/FHIR) по ID записи | Правильный и поддерживаемый путь, права и аудит у МИС | У многих МИС API нет, закрыт или платный ⚠️; у каждой свой | Основной путь для пилота |
| **C. Выгрузка по расписанию** | МИС сама кладёт файл (CSV/XML/JSON) в папку или на SFTP | Не нужен API, простая настройка | Данные не «живые», задержка | Если API нет |
| **D. Чтение базы напрямую** | Коннектор читает реплику БД МИС (read-only) | Все данные, без API | Хрупко при обновлении МИС, риск по лицензии и безопасности ⚠️ | Крайний случай, с согласия вендора |
| **E. Расширение браузера / экранный разбор** | Читает карточку на экране у врача | Не нужен доступ к МИС | Ломается при смене интерфейса, юридически серая зона | Только временно |

**Рекомендация:** прототип на A, пилот на одной МИС через B (или C, если API нет). Выбор МИС — по пилотной клинике: сначала узнать, какая у неё система и даёт ли вендор доступ. Вариант D и E не закладывать в продукт.

## 5. Какие данные брать (принцип минимальности)

Брать только то, что нужно для приёма. По 152-ФЗ и врачебной тайне лишние данные — это риск без пользы.

| Группа | Поля | Зачем |
|---|---|---|
| Приём | дата, врач, специальность, причина записи | Определить шаблон и фокус |
| Пациент | возраст, пол | Контекст для протокола |
| Безопасность | аллергии, непереносимость | Предупреждения |
| История | хронические диагнозы, прошлые визиты (даты, диагнозы по МКБ-10, назначения) | Сводка и сравнение |
| Лекарства | текущие и недавние назначения | Преемственность |
| Результаты | последние анализы и исследования (ключевые показатели) | Контекст |

**Не брать:** паспортные данные, СНИЛС, ИНН, адрес, телефон, данные оплаты, страховки. ФИО передавать в LLM только при необходимости; по умолчанию заменять на код пациента.

## 6. Как объединяем контекст и расшифровку

Главное правило: **контекст — подсказка, а не истина; источник фактов нового приёма — разговор.**

В промпт закладываем:
1. Факты из карты помечены как «из истории», факты из разговора — «со слов пациента на приёме».
2. Если в разговоре данные расходятся с историей — не перезаписывать, а **подсветить** врачу.
3. Каждое утверждение в черновике имеет источник: «из карты (дата)» или «из разговора (время)». Врач одним кликом видит откуда.
4. Нельзя придумывать то, чего нет ни в карте, ни в разговоре; пустые поля остаются пустыми и подсвечены.
5. ИИ не ставит диагноз и не предлагает лечение (граница «не медизделие», см. `mvp_description.md`). Сводка пересказывает историю, а не интерпретирует.

## 7. Безопасность и юридическая сторона

| Тема | Что делаем ⚠️ |
|---|---|
| Идентификация пациента | Данные запрашиваются по ID записи в расписании врача, а не по поиску ФИО; перед приёмом врач видит ФИО и дату рождения и подтверждает «это тот пациент» |
| Доступ | Сводка доступна только врачу, к которому записан пациент, и только в окне приёма (например, за 30 минут до и 2 часа после) |
| Хранение | Контекст в кэше на время приёма, затем удаление; в нашем хранилище остаётся только подписанный протокол и журнал |
| Передача | Шифрование каналов, серверы в РФ; коннектор в контуре клиники отдаёт только разрешённые поля |
| LLM | Данные в модель уходят обезличенными; вариант «модель внутри контура клиники» — для клиник с жёсткими требованиями |
| Согласие | Согласие пациента на запись разговора и на обработку данных ИИ-сервисом; формулировку согласовать с юристом клиники |
| Аудит | Журнал: кто, когда, какого пациента открыл |
| Роли | Врач, администратор клиники (без доступа к медданным, только статистика), поддержка (без доступа) |
| Договор | Клиника — оператор ПДн, мы — обработчик; поручение на обработку, при необходимости уведомление Роскомнадзора ⚠️ уточнить с юристом |

## 8. Влияние на MVP

Это расширение объёма, а не замена. Предлагаю три уровня и выбрать по результатам интервью:

| Уровень | Что входит | Усилия ⚠️ | Что проверяем |
|---|---|---|---|
| **0. Контекст вручную** | Врач вставляет выписку/загружает файл, ассистент строит сводку и черновик | Низкие | Ценна ли сама сводка и «сверка с историей» |
| **1. Чтение из одной МИС** | Автоматическая сводка перед приёмом через API/выгрузку, возврат копированием | Средние (зависит от вендора) | Готовы ли клиники открыть доступ, экономия времени на подготовке |
| **2. Двусторонняя интеграция** | Черновик пишется обратно в МИС в нужные поля | Высокие | Масштабируемость, ценность для сетей с разными МИС |

**Рекомендация:** для демо на интервью — уровень 0 (тестовые карточки). В пилот — уровень 1 на одной МИС. Уровень 2 — после платного пилота. В `mvp_description.md` пункт «Глубокая интеграция с МИС» остаётся «после MVP», но «чтение контекста» переходит в объём.

## 9. Риски и меры

| Риск | Серьёзность | Мера |
|---|---|---|
| **Открыта карточка не того пациента** | Критическая | Данные только по ID записи; подтверждение ФИО и даты рождения врачом; журнал |
| Утечка медданных | Критическая | Минимум полей, обезличивание, РФ-хостинг, кэш с автоудалением, аудит |
| ИИ «пересказал» историю неверно | Высокая | Ссылки на источник у каждого факта; врач проверяет; сводка не интерпретирует |
| Врач слепо доверяет сводке (эффект привязки) | Средняя | Подсвечивать расхождения, обучать, помечать «из истории» |
| Вендор МИС не даёт API или просит деньги | Высокая | Выбирать пилотные клиники по МИС, запасные пути C и A; оценить стоимость доступа заранее |
| У каждой МИС свой формат | Средняя | Единая внутренняя схема + адаптер на каждую МИС |
| Данные в карте неполные или грязные | Средняя | Показывать только то, что есть; не додумывать |
| Задержки (сводка не успела до приёма) | Низкая | Подготовка за 30 минут до приёма и по событию «пришёл»; приём возможен и без сводки |
| Нагрузка/стоимость LLM | Низкая | Сводка строится один раз на приём и кэшируется |

## 10. Что выяснить на интервью и у IT клиники

1. Какая МИС (название, версия) и кто её вендор?
2. Есть ли API, на каких условиях, кто даёт доступ и сколько это стоит?
3. Можно ли ставить коннектор в контуре клиники, или только облако?
4. Что врач сейчас смотрит перед приёмом и сколько на это уходит минут?
5. Какие поля карты реально заполнены, а какие нет?
6. Разрешат ли службы ИБ и юристы передачу обезличенных данных во внешнюю модель?
7. Нужно ли записывать результат обратно в МИС, или копирования достаточно?
8. Готовы ли платить отдельно за интеграцию (как предложила Anna)?

## 11. Следующие шаги

1. Решить в команде: уровень 0 или 1 для демо и пилота (раздел 8).
2. Подготовить 3–5 тестовых карточек пациентов (синтетических, без реальных данных) для демо.
3. Собрать прототип: тестовая карточка + запись разговора → сводка и черновик с источниками.
4. Добавить вопросы раздела 10 в гайд интервью.
5. Определить 1–2 МИС для пилота после интервью и проверить доступ к API.
6. Согласовать с юристом формулировки согласия и схему «клиника — оператор, мы — обработчик».
